    What others do

    • ADI LTpowerPlanner / Power Studio Planner. A drawn power tree where every terminal shows its voltage and current, and each converter shows its efficiency and loss under its block. Clicking a part opens a Properties window (input range, output voltage, maximum load current). A Summary Report gives total input power, output power, loss, and overall efficiency. This lab's Annotated tree and summary strip follow it. (AN-164, article, architecture comparison)
    • TI WEBENCH Power Architect. Loads entered as voltage and current (with ripple) per load; the tool builds the tree, lets branches move from one source to another, and picks parts per branch. (overview, branches)
    • FPGA and SoC estimators (AMD Vivado and Power Design Manager, Intel EPE and PTC). A table of current per supply rail against a per-rail budget, showing positive or negative margin; Intel's PDN guide suggests 30% regulator margin. This lab's Budget table and Headroom follow them. (AMD, Intel)
    • Design notes and templates. A spreadsheet per rail with subtotals and a safety margin; use datasheet maximums, not typicals, to size regulators; count pull-ups and discretes too. (NI PXI, LCSC guide, course template)
    • Battery products. Worst case sizes the regulators; typical predicts battery life. Budgets there add operating modes (active, sleep) with a duty cycle per load and an average current. (power budgets) Not in this lab: it would add a mode column per load. See open questions.

    Where the numbers live: your call

    1. In the Power line's text (what this lab does; the Text capture shows it): 3V3 (sink, 3.0–3.6 V, 80 mA, max 350 mA), 5V (source, 4.85–5.15 V, up to 400 mA, 72%). It rides along with everything Scribe text already does: the command line's scribe.md, the signoff-import skill, draw.io, History, and the section merge. It reads well in the document. Before it ships, the engine's specPowerText must keep the words it doesn't know: today the panel rewrites the line with only the role and no tree, so the numbers would be lost the next time a role changes.
    2. A structured field on the section (power: { "3v3|sink": { vmin, vmax, ityp, imax } }, like ptree). Tidier for code, invisible in the text, and it needs its own merge, command line, draw.io, and History work, and the numbers wouldn't show to someone reading the document.

    Open questions

    • A converter's input current is derived from its outputs (and its efficiency, or quiescent current when linear). Should someone be able to type it instead, for a module with a datasheet input figure?
    • A block with two input rails (a converter after an OR-ing diode, a charger with a power path): which input pays? The lab takes the first and says so.
    • A rail with two sources (a USB path and a battery path into one rail): split the load, take the worst, or one per scenario?
    • Modes beyond Typical and Worst case (Sleep, Charging, Transmit) with a duty cycle and a battery life line?
    • Should a failing budget be a gap on the block (△, in the Gaps filter), a Check note, or only shown here?
    • Should the input limit come from a requirement (the demo's "no more than 1.5 W from mains") rather than a field?
